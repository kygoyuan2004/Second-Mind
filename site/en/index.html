Multiple knowledge bases

One service, several isolated knowledge contexts

Discover one root Vault or its immediate child Vaults beneath an allowed host parent. Every registered directory must be a Vault root with an actual, non-symlink .obsidian directory. Each knowledge base receives a separate index namespace, task context, and write boundary.

A stable ID remains permanently bound to its first canonical Vault path across deletion and restart. A different Vault needs a new ID, including when the host replaces content at the same path.

Current limit: one task binds to one knowledge base. There is no cross-base federated search, and this is not an arbitrary file browser.

BYOK and privacy

Credentials stay server-side, and configuration decides where data goes

Configure model, web search, and embedding credentials independently. Installation makes no paid API calls. Login and local BM25 retrieval still work without model credentials.

  • The browser cannot read a stored key back
  • The static site has no analytics, cookies, or remote fonts
  • Vault files and indexes remain on the host and Docker volumes you manage

Self-hosted does not mean every operation is local-only. When you enable an external model, embedding service, web search, or page reader, selected text, queries, or public URLs go to the matching service. If content must never leave the host, use a browser on that host, use only compatible providers running there, disable web and remote sync, and keep backups in controlled local storage. Review the data flow and provider policy before deployment.

Three-platform quick start

Bring Docker and choose a knowledge base directory

The installer asks only for a Vault or knowledge-base parent, an administrator password, and a port. Its Node logic runs in a container, so the host needs no Node.js installation.

Prerequisites: Git; a conventional rootful Docker Engine with Compose v2 on Linux, or Docker Desktop on macOS and Windows. Rootless Docker or SELinux-enforcing hosts need an administrator-designed UID, volume-permission, and bind-mount relabel policy; the installer does not alter those boundaries automatically.

Docker Engine + Compose v2

git clone https://github.com/kygoyuan2004/Second-Mind.git
cd Second-Mind
./install.sh

PowerShell + Docker Desktop

git clone https://github.com/kygoyuan2004/Second-Mind.git
cd Second-Mind

Use the same entry point after setup: doctorstatuslogsupdatebackup

Operations boundary: backup is a live copy containing credentials, not an atomic app-and-sync snapshot, and it does not collect independent sync state automatically. Restore is manual, update has no automatic image rollback, and there is no permanent uninstall command. To stop services, run docker compose down for the exact instance without --volumes. See the deployment guide.

Current boundaries

Know the operating envelope first

Good fit
One trusted administrator managing personal or small-team knowledge on controlled devices or a private network.
Not provided yet
Multi-tenant accounts, granular team permissions, cross-base federated search, or a managed cloud service.
Network responsibility
Keep access local or private by default. If you publish it, supply TLS, access controls, and backups.
PDF reading
The standard image omits bwrap and pdftotext, so web PDF reading is unavailable by default and never falls back to unsandboxed parsing. Persisting a confirmed PDF attachment is not PDF-content understanding.
Platform integration
No Windows Service or macOS LaunchDaemon is installed, and Credential Manager or Keychain integration is not provided.
